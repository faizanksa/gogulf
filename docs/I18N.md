# Multilingual architecture

Status: **foundation built (Phase 2B close-out, 12 Sep 2026). No language except English is published.**

This page explains how Go Gulf serves more than one language: where the words live, how a language
goes live, how right-to-left works, and what is designed but not built. The code is authoritative;
this page says why it is shaped the way it is.

## Languages

| Code | Language | Tier | Script | Direction | Catalogue status | On the site |
| --- | --- | --- | --- | --- | --- | --- |
| `en` | English (`en-IN`) | source | Latin | ltr | source | yes, unprefixed URLs |
| `hi` | Hindi (`hi-IN`) | primary | Devanagari | ltr | not-started | no |
| `ar` | Arabic (`ar`) | primary | Arabic | **rtl** | not-started | no |

The registry is `lib/i18n/locales.ts`; the codes are also in `lib/i18n/routing.mjs` (plain JavaScript,
so `next.config.mjs` can read it). A unit test keeps the two in step.

## Decisions

- **Next.js's own pattern, not a library.** Next 16.3 ships what a library used to supply: a root
  layout under a dynamic segment (`app/[locale]`) and `next/root-params`, which lets any Server
  Component read the locale without prop drilling. Formatting is ICU MessageFormat through
  `intl-messageformat` (plurals, including Arabic's six forms, select, numbers and dates), on the
  server only. `next-intl` was evaluated. It would add client-side JavaScript and a proxy for routing
  that this site does not need.
- **No client-side translation widget.** No Google Translate, and no machine translation at request
  time. Translations are written ahead of time, reviewed by a person, and served as ordinary page
  content.
- **English URLs do not change.** English is the source and canonical language and keeps its
  unprefixed URLs, served by `app/(marketing)` exactly as before. There are no rewrites and no proxy.
  Other languages are prefixed (`/hi/verify`) and served by `app/[locale]`, a second root layout, so
  every page's `<html lang dir>` is right for its language. `/en/...` redirects permanently to the
  unprefixed path.
- **Nothing is published without review.** A language's routes are built only when its catalogue's
  `$meta.status` is `"reviewed"`, with `reviewedBy` and `reviewedOn` recorded
  (`lib/i18n/catalogs.ts`). A page appears in a language only when the page registry also lists that
  language for it (`content/pages.ts`, `locales`). Today production builds no page under
  `app/[locale]`, and every prefixed URL returns 404.
- **Facts stay language-neutral.** Countries, salaries, dates, job slugs and employment types are
  stored once and only *formatted* per language (`lib/i18n/format.ts`: CLDR country names, `Intl`
  dates and numbers). The following are never translated: the legal company name, CIN, GSTIN, the
  registered address, currency codes, job references, and the brand name and tagline. The claims
  register in `content/` stays authoritative. No translation may add or strengthen a claim.

## Where the words live

| What | Where | Notes |
| --- | --- | --- |
| Interface text (navigation, footer, forms, errors, 404, job-page labels) | `messages/<locale>.json` | ICU MessageFormat. English first; keys are typed from `messages/en.json`, so a missing or misspelt key fails `tsc`. |
| Page titles, descriptions, breadcrumbs | `content/pages.ts` (English), `messages/<locale>.json` → `pages.<id>` | The registry holds the English source; a translation adds `pages.<id>.title` and the other fields. |
| Job text | `content/jobs.ts` → `translations[]` | One reviewed translation per language: title, summary, industry, city. |
| Page body copy | `messages/<locale>.json` → `home.*`, `jobsPage.*`, `candidatesPage.*`, `employersPage.*`, `servicesPage.*`, `aboutPage.*`, `contactPage.*`, `verifyPage.*` | Every page rebuilt in 2C takes all its words from the catalogue. The policy pages keep their English wording in the page: it is legal text, translated only after a legal review. |
| Service names and summaries | `content/services.ts` (English), `messages/<locale>.json` → `services.items.<id>` | Read through `serviceText()`. The enquiry forms send the English name whatever the page's language: the server routes on it. |

Adding a string: add it to `messages/en.json`, use it via `t("namespace.key")`, and the other
catalogues pick it up when their translators next update. An unpublished catalogue may be partial.
A published one must be complete; the unit tests enforce this.

## Server and browser

- Server Components call `getTranslator()` (`lib/i18n/server.ts`), which reads the locale with
  `next/root-params`. Under `app/(marketing)`, `/admin`, `/portal` and the global 404 there is no
  locale segment, which means English.
  - `currentLocale()` never throws. Root layouts and the site shell call it, and a `notFound()`
    thrown there has no boundary to land in; Next would replace the whole page with its bare error
    document.
  - Pages call `requireAvailable(path)` instead. It returns the 404 for an unknown language segment
    or an untranslated page.
- Client Components never import a catalogue. They receive finished strings as props:
  - `SiteNav` gets its labels.
  - Each form (`ContactForm`, `ApplyForm`, `ServiceInquiryForm`, `EmployerRequirementForm`) gets
    one `copy` object built in `lib/i18n/forms.ts`. Values staff read (service names, countries,
    the employer form's composed message) stay English; only the labels are translated.
  - The language islands get a small map of which paths exist in which language.
- UI primitives follow one rule:
  - `Alert`, `Breadcrumbs`, `SkipLink`, `DevNotice` and `OfficialChannels` translate themselves on
    the server.
  - `AlertView`, `Field`, `FormStatus` and `ErrorSummary` take their words as props, for use inside
    client islands.
  - `Button`'s `external` and `opensWhatsApp` props carry the translated screen-reader note.
- Route Handlers cannot read `next/root-params`, so a form sends its page's language in an
  `X-Form-Locale` header. The endpoint URL stays the same in every language.
  The handler (`lib/forms/handler.ts`) answers in that language, including validation errors: the
  Zod schemas carry catalogue keys, and `toFieldErrors` translates them.

With one active language (production today), neither language island renders. Their code still ships:
measured on a production-stage build (12 Sep 2026), 1.2 KB gzip of shared JavaScript and 0.5 KB of CSS
on every page. A Server Component cannot code-split a Client Component it imports (`next/dynamic`
does not help there). Dropping the code while one language is published needs a build-time flag;
that is a 2C follow-up.

## Right-to-left

Arabic is right-to-left at the document level, not by translating strings into a left-to-right
layout:

- `<html lang="ar" dir="rtl">`, from the registry (`components/site/RootDocument.tsx`).
- Component CSS uses logical properties: `margin-inline-start`, `padding-inline-end`,
  `border-inline-start`, `inset-inline`. Layout follows the direction without per-component
  overrides. The one exception is a background image position, which has no logical form
  (`Controls.module.css`).
- Arrows and chevrons mirror under `dir="rtl"` (`Icon`: `arrow-right`, `chevron-right`).
- Phone numbers, CIN and GSTIN are wrapped in `<bdi dir="ltr">` (`LtrText`). Without it, the bidi
  algorithm reorders `+91 99363 09015` inside Arabic text.
- Arabic headings run at normal width, and Arabic text gets more leading (`styles/tokens.css`,
  `styles/base.css`). `:lang(ar)` also matches `ar-XB`, so right-to-left testing sees both.
- The Arabic typeface (Noto Sans Arabic) is added with the first reviewed Arabic catalogue, not
  before. Every declared font family puts its `@font-face` rules on every page; Arabic and Malayalam
  together measured 1.5 KB gzip of CSS on English pages (12 Sep 2026). Until then Arabic renders in
  the system's Arabic font.
- Salary ranges and dates are not forced left-to-right. In Arabic text the bidi algorithm orders a
  range such as 3,500 – 4,500 correctly for a right-to-left reader.
- Western digits are used for salaries, dates and references in every language. If the Arabic
  reviewer prefers Arabic-Indic digits, that is one setting in `lib/i18n/format.ts`.

The legacy pages (`(legacy)`, `(legal)`) use physical CSS and are English-only. They get no
`app/[locale]` route until they are rebuilt.

**Testing without translations: pseudo-locales.**
- `/ar-XB/...` renders the site right-to-left with every catalogue string wrapped in a
  right-to-left override. A page that still reads correctly there mirrors correctly.
- `/en-XA/...` accents and lengthens every catalogue string by about 30%. Any plain English left on
  the page is text that has not gone through the catalogue; any clipped label is a layout that will
  break in Malayalam.
- Both are built only on local and staging builds, are `noindex`, and never appear in hreflang or the
  sitemap.

**Build gate: `npm run build:production-stage`.** This builds as production does: no pseudo-locales and
no unpublished language, so `app/[locale]` generates nothing. Local and staging builds cannot show a
failure that only happens when a language layout is empty. Run it before anything reaches `main`. It
caught one on 12 Sep 2026: a nested `generateStaticParams` read the `next/root-params` getter, which
throws when the parent generated no params. Nested segments read `params` from their argument instead.

## Choosing a language

- **Language menu** (`components/site/LanguageMenu.tsx`):
  - On desktop it is a disclosure button in the header; on phones it is a list inside the menu panel.
  - It shows only on pages that exist in more than one language.
  - Each option is a link with its own `lang` and `hreflang`, so a screen reader pronounces "हिन्दी"
    as Hindi. The current language is marked `aria-current`.
  - Escape closes the menu and returns focus to the button.
- **Language suggestion** (`LanguageSuggestion.tsx`):
  - When the page also exists in the reader's language, a small fixed card offers it, written in that
    language.
  - "The reader's language" is the one they chose in the menu, otherwise the first *published*
    language in their browser settings.
  - It never redirects, shifts no content, and a dismissal is remembered.
- **Preference** (`lib/i18n/preference.ts`): stored in `localStorage` (`gg-lang`), never in a cookie
  (the privacy policy promises none), and never sent to the server.

## Search engines

- **Canonical:** each language version is canonical to itself (`/hi/verify` → `/hi/verify`).
- **hreflang:** emitted only when a page exists in two or more real languages. `x-default` points to
  English. Pseudo-locales are excluded (`hreflangAlternates`).
- **Sitemap:** one entry per language version, each listing all the others as alternates (`app/sitemap.ts`).
- **Open Graph:** `og:locale` comes from the registry (`en_IN`, `hi_IN`, `ar_AR`, …).
- **JobPosting:** appears only on the English job page. Translations are its hreflang alternates, and
  structured data must match its page word for word.

## Jobs: today and Phase 5

Today the jobs are files (`content/jobs.ts`). Each job has an optional `translations` array. A
translation is used only when `status: "reviewed"`, with `reviewedBy` and `reviewedOn` set. A job page
in a language exists only when such a translation exists (`app/[locale]/jobs/[slug]`).

Phase 5 moves jobs to Supabase behind the same functions. The intended shape is below; it is
**a design, not a migration**, and nothing has been applied anywhere:

```sql
create table public.job_translations (
  job_id       uuid not null references public.jobs (id) on delete cascade,
  locale       text not null check (locale in ('hi', 'ar', 'ml', 'ta', 'bn')),
  title        text not null,
  description  text not null,          -- today's `summary`
  requirements text,
  benefits     text,
  industry     text,
  city         text,
  status       text not null default 'draft' check (status in ('draft', 'in-review', 'reviewed')),
  reviewed_by  uuid references public.staff (id),
  reviewed_on  date,
  primary key (job_id, locale),
  check (status <> 'reviewed' or (reviewed_by is not null and reviewed_on is not null))
);
```

Country, salary, dates, employment type and slug stay on `jobs`. Only reviewed rows are public (RLS).

## CRM and WhatsApp (not built)

- `contacts.preferred_language` already exists (`supabase/migrations/0003_identity.sql`, default
  `'en'`).
- When the forms write to the CRM (Phase 3+), the submission's `locale` becomes the initial preferred
  language.
- Acknowledgement emails and WhatsApp templates would then be chosen per language. Each template
  needs a reviewed translation, like any other page.

The acknowledgement emails are English today. The prefilled WhatsApp messages from the header and
job pages are already in the page's language.

## Adding a language

1. Commission the translation of `messages/en.json` into `messages/<code>.json`. Keep the ICU
   arguments and tags; the tests check them.
2. Have a native speaker review it. Set `$meta.status` to `"reviewed"` with `reviewedBy` and
   `reviewedOn`. The language becomes active and `app/[locale]` builds its routes.
3. For each page to publish in it, translate its body copy into the catalogue, add `pages.<id>`
   (title, description, breadcrumb) and add the code to that page's `locales` in `content/pages.ts`.
4. For each job, add a reviewed entry to its `translations`.
5. Add the script's typeface in `app/fonts.ts` (Noto Sans Arabic, Anek Malayalam, Anek Tamil, Anek
   Bangla; Hindi's is already there), non-preloaded and with `adjustFontFallback: false`. Add its
   `:lang()` stack in `styles/tokens.css` in the same change.
6. Run the tests, then check the pages on staging with the pseudo-locales and a native reader.

## Known gaps

- No real language is published yet: every catalogue other than English is a draft awaiting a
  native reviewer. The pseudo-locales show every page fully through the catalogue.
- The policy pages are English-only and have no `app/[locale]` route; their wording is legal text.
- A path under a language prefix with no page (for example `/ar-XB/pricing`) gets the English global
  404 (`app/global-not-found.tsx`). There is deliberately no catch-all route under `app/[locale]`.
  A dynamic catch-all also catches every miss from a `dynamicParams = false` route, such as an
  unknown job slug, and renders it under a language layout. Tried and removed on 12 Sep 2026.
- `/travel` has no route until decision D2 (removed in 2C). It is an unknown URL, so it gets the
  fully server-rendered 404. A page-level `notFound()` in a prerendered page is server-rendered as
  Next's error document instead, which is why the placeholder page was taken out rather than kept.
- The job-seeker FAQ restates published policy only. `content/faqs.ts` stays empty until the
  business supplies approved answers.
- Undecided: Arabic digits (Western or Arabic-Indic), whether the tagline "Go Gulf. Get Hired." is
  ever translated, and translated acknowledgement emails.
